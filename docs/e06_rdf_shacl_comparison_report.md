## 1. 목적과 범위

E05(Python/Pydantic, SQLite)와 **같은 평가셋·정답·채점기·환경**에서 RDF(rdflib 7.6.0) + SHACL(pyshacl 0.40.1)이 추가로 주는 이익과 비용을 잰다. GraphDB·OWL 추론·UI는 범위 밖. 비교 방식: `shacl_pyshacl`(본 결과), `shacl_hybrid`(Core는 pyshacl, SPARQL 규칙은 같은 질의를 rdflib로 규칙당 1회 — 엔진 비용 분리용), `shacl_core_compare`(두 속성 비교를 Core 제약으로 쓴 변형).

## 2. RDF 데이터 매핑 구조

- 레코드 노드 `rec/{record_uid}`(원본 레코드 1건 = 노드 1개)와 업무 키 노드 `id/{엔터티}/{키}`를 분리. 마스터 레코드가 있을 때만 키 노드에 `rdf:type` → 참조 대상이 없으면 실체를 만들지 않고 `sh:class`가 누락을 잡는다.
- 정상 데이터(E01 v2): 레코드 353 → **4,668 트리플**(계보 포함, `clean_graph.nt` 761,794 bytes). 왕복 불일치 0, 72개 데이터셋 재생성 해시 72/72 일치.
- 어휘(`ontology/e06_minimal.ttl`) 175줄, 엔터티 14종(레코드 클래스 14 + 마스터 클래스 7).

## 3. SHACL 규칙과 E05 대응

- E05 채점 규칙 41개 전부에 shape를 만들었다: **shape 418개 (Core 377, SPARQL 41)**, 규칙 기준 Core 21개·SPARQL 20개. V13(생산능력 계산)은 SHACL로 옮기지 않음(분류 4), NOT_MEASURED 6개는 규칙 없음.
- 모든 shape에 `cp:ruleId`·`cp:fieldName`·`cp:engine`을 달아 검증 결과를 E05 규칙 ID로 명시적으로 대응(대응 실패 0).
- Core로 표현 가능하지만 SPARQL로 바꾼 규칙: B05·V02·V07 — pyshacl이 비교 대상에 형식 오류 리터럴이 있으면 검증 전체를 중단하기 때문 (§5).

## 5. 확인된 SHACL·RDFLib 결함과 의미 차이

| 항목 | 내용 | 영향 |
|---|---|---|
| 리터럴 해석 관대함 | rdflib가 `NaN`·`INF`·`1e3`·`' 12'`·전각 숫자·`1_000`을 정상 xsd:decimal로, `2026-11-15T00:00`을 정상 xsd:date로 받아들임 → `sh:datatype`도 위반으로 보지 않음 | E05 Pydantic lax 모드와 같은 종류의 결함. SQLite 질의는 모두 거부 |
| Core 비교 제약 중단 | `sh:lessThanOrEquals`는 형식이 틀린 날짜가 있으면 TypeError, `sh:minInclusive`는 NaN에서 InvalidOperation으로 **검증 전체 중단** | Core 변형에서 I-S03a·C-3 중단 → 그 데이터셋의 다른 오류까지 모두 놓침(ERROR FN 9) |
| SHACL-SPARQL 제한 | `$this`를 고르지 않는 중첩 SELECT 금지 → 집계(B12)를 `GROUP BY $this … HAVING`으로 다시 써야 함 | 표현은 가능하나 집계 비용 증가 |
| 속성 경로 한계 | 경로 중간 단계에 조건(BOM 승인·활성, component_type)을 걸 수 없음 | B01 의미 차이(평가셋 영향 없음), Q2 naive 경로식은 판별 사례에서 오답 |
| 열린 세계 | "없는 대상"은 변환기가 마스터에서만 타입을 만든다는 폐쇄 규칙에 의존 | 다른 그래프를 합치면 판정이 바뀔 수 있음 |

## 10. Python/SQLite 대비 추가 이익 (실측 기준)

- 오류 검출: **추가 이익 없음** (같은 정답셋에서 검출 차이 0).
- 관계 조회: 정답률 같음. SPARQL 경로식은 짧지만 조건부 간선에는 CONSTRUCT 선처리가 필요해 재귀 CTE보다 단순하다고 보기 어려움.
- 규칙 변경: 수정 범위 같음.
- 미정의 속성 보존(SC5): RDF만 값이 남음 — 이점 후보이나, 다기업 의미 통합 요구가 확인되기 전에는 판단 근거로 약함.
- 선언적 규칙 표현(Core shape): 필수·타입·열거·범위·참조는 읽기 쉬운 선언으로 표현됨. 단 같은 것을 SQL/Pydantic도 모델에서 생성하고 있어 실익 차이는 측정되지 않았다.

## 11. RDF/SHACL 도입 부담

- 성능: L(1.7만 레코드)에서 검증 70분 — Python 0.2 s 대비 운영 배치로 쓰기 어려운 수준(목표값 미합의라 PASS/FAIL 판정은 하지 않음).
- 메모리: L에서 약 0.7 GB (Python·SQLite 약 56~59 MB).
- 엔진 위험: 형식 오류 데이터에서 검증 전체 중단(Core 비교 제약), 리터럴 해석 관대함.
- 추가 설계: URI·키 노드 정책, 폐쇄 세계 판정 규칙, 결과 → 레코드 대응, SPARQL 질의 튜닝.

## 12. E07 GraphDB가 필요한 조건

experiment_plan.md E07 재개 조건 중 이번 실측과 관련된 것: ① "RDFLib가 관계 조회 규모·속도를 충족하지 못함" — **관계 조회(SPARQL)는 L에서 0.27 s로 충족**, 느린 것은 pyshacl 검증 엔진이며 GraphDB가 이 문제를 푸는지는 미측정. ② 전용 저장소 관리 기능, ③ 다중 시스템 의미 통합, ④ 관계형 DB 대비 정량 이점 — 모두 확인되지 않음. → **E07 재개 조건 미충족, 보류 유지.**
