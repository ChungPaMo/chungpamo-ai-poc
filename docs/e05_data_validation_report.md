## 6. SQLite 결과

| 방식 | ERROR TP/FP/FN | Precision | Recall | F1 | 사건 | 규칙 검출/기대 | WARNING TP/FP/FN |
|---|---|---|---|---|---|---|---|

- **외래키 설정**: SQLite 3.45.1 `PRAGMA foreign_keys` 기본값 0 확인 → 제약 모드에서 `ON`으로 켜고 값 1을 확인(정상 데이터 적재 거부 0). 끄면 FK 위반이 조용히 적재된다 (테스트 `test_sqlite_foreign_keys_default_off_and_pragma_on`).
- **날짜 함정**: `date('2026-02-30')`은 오류가 아니라 `2026-03-02`를 반환한다. `date(x) = x` 왕복 비교로만 존재하지 않는 날짜를 잡을 수 있다.
- **제약 모드 한계(실측)**: ① 행당 첫 위반만 보고 — C-3 주문 O015의 상태 오류(S04) 미보고, I-S01b 빈 문자열이 S01이 아니라 S03으로 보고(부분 탐지) ② 연쇄 거부 — 부모 행이 거부되면 자식 행이 모두 FK 실패: 오탐 114건 전부 이 유형(예: I-B14 제품 1건 거부 → 92행 거부) ③ 관계·집계 규칙(B01, B02, B04, B06, B08~B12, V08, V09, V11, V12) 표현 불가 ④ FK 실패 메시지에 열 이름이 없음 — 부모 테이블을 다시 조회해 열을 특정해야 함.

| 분류 | 규칙 |

## 8. False Positive / False Negative 사례

### 8.1 정확하게 검출한 오류
python_full·sql_queries: 기대 항목 104개(ERROR 99 + WARNING 5) 전부. 파생 보고 65건(예: BOM 기간 변경으로 계획 라인 B06 선택 불가 11~12건), 허용 보고 25건은 오탐에서 제외.

### 8.2 놓친 오류 (FN)
- python_full·sql_queries: 0
- pydantic_only: 72건 (ERROR 68, WARNING 4) — 검출 불가 규칙 24개, C-3 B05 가림
- sql_constraints: 54건 (ERROR 49, WARNING 5) — 표현 불가 관계 규칙 14개 + 행당 첫 위반만 보고(C-3) + 연쇄 상황에서 원인 행 누락

### 8.3 잘못 탐지·판정이 엇갈린 사례
- **FP 1건 (python_full·sql_queries 공통, WARNING)**: I-S08c 복합 키 중복에서 *원래* 레코드 쪽 B10(같은 구성품 중복) 보고. 정답의 `acceptable`이 주입 레코드만 포함한 정의 한계로 판단되지만, 결과를 본 뒤 정답을 바꾸지 않고 오탐으로 집계했다.
- **FP 114건 (sql_constraints)**: 전부 연쇄 거부 (부모가 먼저 거부되어 자식 FK 실패). 입력에는 부모가 있으므로 데이터 오류가 아니다.
- **평가셋 밖 보조 관찰 — Pydantic(기본 lax 모드)의 형식 수용 (결함)**: `Material.unit_cost`에 `'NaN'`, `'Infinity'`, `'1e3'`, `' 12'`, `'+5'`, `'１２'`(전각), `'1_000'`을 넣으면 Pydantic은 Decimal로 받아들여 오류를 내지 않았다 (`NaN`은 `ge=0` 제약도 통과). `Order.order_date = '2026-11-15T00:00'`도 날짜로 받아들였다. SQL 질의는 모두 S02·S03으로 거부해 두 방식 판정이 21개 중 9개에서 엇갈렸다 (`summary.md` 보조 관찰 표). 평가셋에 이런 값이 없어 정확도 수치에는 반영되지 않았다. **Pydantic을 구조 검증에 쓰려면 strict 모드·유한값 검사 등 추가 조건이 필요하다** (E01 모델은 수정하지 않음 — 수정 여부는 승인 사항).

### 8.4 여러 오류가 서로 영향을 준 사례
- C-2: BOM 라인 전부 삭제 뒤 순환 라인을 추가하면 "라인 없는 BOM"(B09)이 성립하지 않는다 — 연산 순서가 정답을 바꾼다 (정답에서 제외, 네 방식 모두 B09 미보고 = 정상).
- C-3: Pydantic model_validator 가림(§5), SQLite 첫 위반만 보고(§6).
- 연쇄 영향: 자재 마스터 삭제 → 고아 참조 3건(I-R02c), BOM 기간 변경 → 계획 라인 선택 불가 다수(I-B06 등), 공정 삭제 → 계획 라인 자원 불일치 12건(I-V08). 채점에서 파생으로 분리.

### 8.5 기존 정의가 불충분해 판정할 수 없는 사례
- 빈 문자열과 null의 구분(S07), 라인 없는 BOM(B09), 같은 구성품 중복 라인(B10), 외주 불가 제품의 외주 라인(V11), 계획 기간 밖 라인(V12) → 합성 가정 WARNING
- 업무 ID 형식, 주문 수량 허용 범위, 공급 계약 → NOT_MEASURED
- 배분 비율 합 허용오차(B12), 오류 코드 ERR-ENUM·ERR-IDFMT → 팀 합의 필요
- 숫자·날짜 문자열의 허용 표기(§8.3) → 기준 문서 없음, 팀 합의 필요

| 규칙 수정 | 함수 1개 수정. 모델 제약은 E01 모델과 공유돼 수정 시 E01 영향 | 질의 1개 수정. 구조 규칙은 모델에서 생성되므로 모델 변경이 자동 반영. 제약 모드는 테이블 재생성 |
| 오류 추적 | record_uid·필드·근거(evidence: 순환 경로, 겹치는 버전 등) 직접 보고 | 질의 결과로 record_uid·필드 보고 가능. 제약 모드는 행당 첫 위반·FK 열 미상 |
| 유지관리 | 규칙과 모델 검증이 섞이면 가림 발생 → 업무 규칙은 독립 함수로 유지해야 함 | 날짜·숫자 판정을 SQL로 재정의해야 해 Python과 기준이 어긋날 위험 (§8.3), FK pragma 연결마다 설정 |

코드 줄 수만으로 우열을 판단하지 않는다. 같은 규칙을 두 번 구현했으므로 두 방식의 판정이 같다는 것이 상호 검증 역할을 했다 (형식 경계에서만 차이).

## 11. Python/SQL의 장단점

| | 장점 | 단점 |
|---|---|---|
| Pydantic | 기존 모델 재사용, 타입·범위·조건부 필수를 선언적으로 표현 | 레코드 하나만 봄, model_validator 가림, lax 모드가 NaN·지수·전각 숫자 수용 |
| Python 독립 함수 | 관계·재귀·집계·근거 보고가 자유로움, 계층 분리 쉬움 | 규칙마다 코드 작성, 대규모에서는 메모리 내 처리 한계(미측정) |
| SQLite 질의 | 집합 연산(참조·중복·집계)이 짧음, 재귀 CTE로 다단계 BOM, 운영 DB로 옮기기 쉬운 형태 | 형식 판정 재정의 필요, SQLite 고유 동작(date 정규화, FK 기본 off), 운영 DB와 방언 차이 |
| SQLite 제약 | 적재 시점 방어, 선언적 | 첫 위반만, 연쇄 거부, 관계 규칙 불가 → 검증 보고 수단으로 부적합 |

## 14. 기술 선정 관점의 판단

판정은 PoC 범위의 잠정 판단이며 운영 기술 채택이 아니다.

| 기술·방식 | 판정 | 근거 / 조건 |
|---|---|---|
| Pydantic (E01 모델) — 구조 검증 계층 | **조건부 채택** | 기존 모델 재사용, 구조 규칙 정확. 조건: strict 모드 또는 유한값·표기 검사 추가(§8.3), 업무 규칙과 분리 |
| Pydantic 단독 검증 | **제외** | 재현율 0.313, 참조·관계·집계 불가 |
| Python 독립 규칙 함수 | **조건부 채택** | 평가셋 41규칙 전부 검출, 근거 보고 가능. 조건: 실제 업무 규칙 확정, 운영 규모 성능 확인 |
| SQLite 검증 질의 | **조건부 채택** (PoC·배치 검증용) | 41규칙 전부 검출, 재귀 CTE로 BOM 순환. 조건: `PRAGMA foreign_keys`·날짜 왕복 비교 등 SQLite 고유 동작 관리, 운영 DB 확정 후 방언 재검증 |
