# 데이터 출처·실제/합성 구분 정책 — E01

- 작성일: 2026-10-20 (E01 명세 단계, 검토 대기)
- 이 문서는 **규칙(무엇을 지켜야 하는가)**을 정한다. 추적 구조(어떻게 기록하는가)는 [data_provenance_design.md](data_provenance_design.md)에 있다.

## 1. 데이터 출처 분류

모든 데이터셋과 레코드는 아래 분류 중 하나를 가진다(`origin_class`).

| 분류 | 정의 | 예 | 저장 위치 | Git 추적 |
|---|---|---|---|---|
| `PUBLIC_REAL` | 공개된 실제 데이터 원본 그대로 | UCI 원본 CSV, M5 원본 CSV | `data/raw/public/<dataset>/` | 아니오 (원본 파일). 매니페스트만 추적 |
| `PUBLIC_DERIVED` | 공개 실제 데이터를 **값의 의미를 유지한 채** 형식만 바꾼 것 (열 이름 변경, 형식 변환, 기간 자르기). 대상·측정 단위가 원본과 같음 | UCI 일별 총주문 60행을 `day_index`, `total_orders` 열로 정리 | `data/synthetic/public_derived/` | 라이선스 확인 후 결정 (UCI는 가능) |
| `SYNTHETIC` | 정답 원천에서 생성한 가상 데이터. **공개 데이터 값을 가상 제품에 배분·대응시킨 값도 여기에 속한다** (`generation_method` = `ALLOCATED` / `MAPPED`, 원본 링크 필수) | 합성 BOM, 재고, 공급사 / UCI 총주문을 제품 5종에 비율 배분한 값 | `data/canonical/`, `data/synthetic/`, `data/vendor_a/`, `data/vendor_b/` | 예 |
| `SYNTHETIC_INJECTED` | 합성 데이터에 의도적으로 오류를 넣은 것 | 중복 ID 주입본 | `data/invalid/` | 예 |
| `MANUAL` | 사람이 별도로 만든 자료 (정답 원천에서 자동 생성되지 않음) | 한글 프로그램으로 별도 제작한 HWP | `data/documents/` | 예 (비공개 요소 없을 때) |
| `COMPANY_REAL` | 실제 기업 데이터 | 수요기업 제공 자료 (현재 없음) | `data/raw/` 하위만 | **아니오** |

- 정답 데이터(`data/ground_truth/`)는 생성 원천에 따라 위 분류를 그대로 물려받고, 사람이 검수한 정답은 `MANUAL` 검수 기록을 추가한다.
- 분류는 레코드 단위로 기록한다. 한 데이터셋 안에 분류가 섞이면(예: 공개 수요 + 합성 BOM) 데이터셋 분류는 `MIXED`로 하고 구성 비율을 매니페스트에 적는다.

## 2. 표기 규칙

1. 보고서·발표·결과 파일에서 결과를 인용할 때 데이터 분류를 함께 적는다. 합성 데이터 결과를 "현장 성능" 또는 "실제 기업 데이터 결과"로 표현하지 않는다.
2. `PUBLIC_DERIVED` 결과는 "공개 데이터(출처명) 기반 파생"으로 표기하고, 원본 데이터의 업종(M5 = 소매, UCI = 물류)이 제조업과 다르다는 점을 함께 적는다.
3. 합성 데이터의 설계 가정(단위, 리드타임 범위, 비용 단가 등)은 매니페스트에 기록하고, 결과 해석 시 가정임을 밝힌다.
4. 출처를 확인하지 못한 값은 `미확인`으로 둔다. 2차 출처로만 확인한 구조는 `2차`로 표시한다([data_source_research.md](data_source_research.md) §0).

## 3. 라이선스·접근 규칙

| 데이터 | 라이선스 상태 | 사용 조건 |
|---|---|---|
| UCI Daily Demand Forecasting Orders | CC BY 4.0 [확인] | 출처 표기(인용·DOI) 필수. 가공·재배포 가능 |
| Kaggle M5 | **미확인** (대회 규칙 원문 미확인) | 사용자가 규칙을 확인·동의하기 전에는 다운로드·사용 금지. 확인 후에도 원본은 Git에 올리지 않음 |
| QUDT 단위 어휘(참조 시) | CC BY 4.0 [확인, qudt.org] | 출처 표기 |
| 팀 내부 비공개 원본 문서(PDF/DOCX) | 비공개 | 내용을 데이터로 사용하지 않음, Git 추적 금지 |

- 새 공개 데이터는 사용 전에 라이선스와 재배포·상업적 이용 제한을 확인하고 이 표에 추가한다.

## 4. 공개 데이터 활용 기준

공개 판매·주문 데이터를 합성 제품의 `SalesHistory`에 쓸지는 **아직 결정되지 않았다**. 쓴다면 아래 규칙을 지킨다.

### 4.1 데이터별 해석 범위

| 데이터 | 취급 | 금지 |
|---|---|---|
| UCI Daily Demand Forecasting Orders | **일별 집계 주문 자료** (브라질 물류 회사, 60일, 하루 1행). 목표 변수 `Target (Total orders)`는 그날의 총주문량 | 개별 제품별 주문으로 해석하지 않는다. `Order type A/B/C`, 업종별 주문 열을 제품·자재로 대응시키지 않는다. 원본에 없는 달력 날짜를 원본 값처럼 표기하지 않는다(날짜 부여는 합성 가정) |
| Kaggle M5 | 소매 품목×상점×일 판매 수량 [2차] | 라이선스 확인 전 사용 금지. 사용하더라도 제조 제품의 실제 수요로 표기하지 않는다 |

### 4.2 원본값과 배분된 합성값의 분리

1. **원본 보존**: 공개 원본은 원래 컬럼 그대로 스테이징 레코드(`stg_public_*`, 원본 1행 = 1레코드, `record_uid` 부여, `origin_class = PUBLIC_REAL`)로 보존한다. 값을 고치지 않는다.
2. **배분 레코드는 별도 생성**: 원본 1행의 총량을 가상 제품 n종에 나누면 제품별 n개 `SalesHistory` 행을 새로 만든다. 각 행은
   - `origin_class = SYNTHETIC`, `generation_method = ALLOCATED`
   - `derived_from_record_uid` = 원본 스테이징 레코드
   - `allocation_share` = 배분 비율 (합성 가정값). 같은 원본에서 나온 행들의 비율 합 = 1
   - 배분된 수량 = 원본 총량 × `allocation_share` (반올림 규칙은 매니페스트에 기록)
3. **합계 검증**: 배분 행 수량의 합이 원본 총량과 같은지(반올림 차이 처리 포함) 생성 시 검사하고 결과를 매니페스트에 남긴다.
4. **배분 비율의 근거**: 비율은 합성 가정이므로 생성 파라미터(고정 비율 또는 시드 기반 난수)와 시드를 기록한다. 비율을 "실제 제품 구성비"로 표현하지 않는다.
5. **보고 표기**: 배분 데이터를 쓴 결과는 "공개 일별 총주문(UCI)을 가상 제품에 배분한 합성 수요"로 적는다. 원본 업종(물류)이 제조업과 다르다는 점을 함께 적는다.
6. **M5를 쓰는 경우**: 원본 시계열 1개를 가상 제품 1개에 대응시키면 `generation_method = MAPPED`, 원본 시계열 ID(`source_series_id`)와 크기 조정 계수를 기록한다. 이것도 `SYNTHETIC`이다.

### 4.3 결합 데이터셋 표시

원본에 없는 BOM·재고·리드타임과 결합한 데이터셋은 `MIXED`로 표시하고 구성(공개 파생 / 배분 합성 / 순수 합성 레코드 수)을 매니페스트에 적는다. 이 결정은 라이선스 확인(M5)과 산업데이터·KPI 조사 담당의 공개 데이터 조사 결과를 보고 내린다.

## 5. 외부 전송 규칙

- 외부 API(Upstage, LLM 등)에는 `SYNTHETIC`, `SYNTHETIC_INJECTED`, 라이선스가 허용하는 `PUBLIC_REAL`/`PUBLIC_DERIVED`만 보낼 수 있으며, 그것도 해당 실험의 API 사용 승인(D-007 등) 후에만 가능하다.
- `COMPANY_REAL`은 반출 승인·계약·보존 정책 확인 전 어떤 외부 서비스에도 보내지 않는다.

## 6. 버전·불변성 규칙

- 정답 원천과 원본 파일은 SHA-256 해시로 동결한다. 변경하면 데이터셋 버전을 올리고, 이전 버전 기준 결과는 재실행 또는 `INVALID` 처리한다([evaluation_protocol.md](evaluation_protocol.md) §2.3).
- 원본 파일은 수정하지 않는다. 모든 정제·변환 결과는 새 파일로 만든다.
