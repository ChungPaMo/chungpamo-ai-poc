# 평가 프로토콜 — 충파모 과제 7 사전 기술 PoC

- 작성일: 2026-10-20 (1단계 초안)
- 개정: 2026-10-20 2단계 보완 — 탐지 판정·중복 보고 집계·오탐 분리(§4, §4.1), 병합 셀·페이지 넘김 표(§3.4, §3.5), E00 재현성 기준(§9)
- 개정: 2026-10-20 E01 보완 — 오류 코드 5종 추가(§2.4), CQ 연계(§5.2), E06·E07 동일 조건 비교 항목(§5.4)
- 개정: 2026-10-20 문서 파싱 범위 확정(CSV·XLSX·DOCX·PDF·HWP·HWPX·PPTX) — 형식별 검증 항목·지표(§10)
- 적용 범위: E01~E09 전 실험
- 원칙: 동일 입력·동일 정답·동일 지표로 비교한다. 측정하지 않은 값은 `미측정`으로 기록하며 0이나 추정치로 채우지 않는다. 목표값은 근거 없이 정하지 않고 `팀 합의 필요`로 남긴다.

## 1. 공통 기록 규칙

### 1.1 값 표기

| 상황 | 표기 | 예 |
|---|---|---|
| 측정 완료 | 숫자 + 단위 | `0.912`, `1.84 s` |
| 측정하지 않음 | `미측정` | 메모리 측정 도구가 없어 측정 못 함 |
| 측정 시도했으나 실패 | `측정실패(사유)` | `측정실패(프로세스 조기 종료)` |
| 구조상 측정할 수 없음 | `측정불가(사유)` | API 서버 측 메모리 → `측정불가(서버 측)` |
| 분모가 0 | `N/A(분모 0)` | 해당 문서에 표가 없을 때 표 셀 일치율 |
| 해당 없음 | `해당없음` | CSV 파서의 API 호출 수 |
| 외부 정보 확인 전 | `미확인` | API 실제 청구 비용, 라이선스 조건 |

- 비율은 0~1 소수 셋째 자리까지 기록하고, 반드시 **분자/분모**를 함께 남긴다. 예: `0.900 (18/20)`.
- `N/A(분모 0)`는 0%도 100%도 아니며, 평균 계산에서 제외하고 제외한 건수를 별도로 적는다.
- 집계(평균 등)는 **마이크로 평균(전체 분자 합 / 전체 분모 합)**을 기본으로 하고, 필요 시 파일별 값을 함께 제공한다.

### 1.2 "출력 생성"과 "정확 추출"의 구분

모든 파서·변환 결과는 다음 세 단계를 별도 열로 기록한다.

| 열 | 의미 | 판정 |
|---|---|---|
| `run_ok` | 예외·타임아웃 없이 프로세스가 종료됨 | True/False |
| `output_generated` | 비어 있지 않은 결과 파일(텍스트/JSON/표)이 생성됨 | True/False |
| `extraction_correct` | 정답셋과 비교한 지표(아래 §3) | 비율 |

`output_generated = True`라도 정확도 지표는 별도로 계산하며, "출력이 나왔다"는 사실을 성공으로 보고하지 않는다.

### 1.3 실험 실행 기록 (모든 실험 공통 메타데이터)

각 결과 파일에는 다음을 포함한다: 실험 ID, 실행 일시, 실행자, Git 커밋 해시(저장소 구성 후), Python 버전, 패키지 버전 목록(lock 파일 경로), 입력 데이터 해시(SHA-256), 정답셋 버전, 반복 횟수, 난수 시드, 실행 장비(environment_inventory.md 기준), 백그라운드 부하 상태 메모, 실험 상태(§7).

## 2. 공통 데이터 기준 (E01에서 구성)

> 1단계에서는 **설계만** 한다. 실제 데이터·문서 샘플은 E01에서 승인 후 생성한다.

### 2.1 제조업 가상 시나리오 엔터티

> E01 명세(2026-10-20)로 상세 정의는 [manufacturing_data_schema.md](manufacturing_data_schema.md)가 대체한다. 아래 표는 1단계 초안으로 남겨 둔다.

| 엔터티 | 주요 필드(초안) | 초기 규모 |
|---|---|---|
| 제품 Product | product_id, product_name, unit, doc_version | 5종 |
| 자재 Material | material_id, material_name, base_unit(kg 등), supplier_id | 10종 |
| BOM | product_id, material_id, qty_per_unit, unit | 약 20행 |
| 주문 Order | order_id, product_id, qty, due_date | 팀 합의 필요 |
| 재고 Inventory | item_id(제품/자재), on_hand_qty, unit, as_of_date | 제품 5 + 자재 10 |
| 생산능력 Capacity | resource_id, product_id, capacity_per_period, period | 팀 합의 필요 |
| 리드타임 LeadTime | material_id, supplier_id, lead_time_days | 자재 10 |

- 모든 레코드는 `product_id / material_id / order_id` 등 ID로 연결한다.
- 다단계 BOM(반제품 포함) 여부는 `팀 합의 필요`. GraphDB 2~3단계 관계 조회 실익을 보려면 최소 1개 이상의 다단계 구조가 필요하다는 점을 E07 검토 시 고려한다.

### 2.2 업체별 표현 차이 (동일 개념의 이형 표현)

동일한 정답 사실을 서로 다른 두 업체(가칭 Vendor A, Vendor B)의 CSV/Excel로 표현한다.

| 차이 유형 | Vendor A 예 | Vendor B 예 |
|---|---|---|
| 컬럼명 | `product_id`, `material_id`, `qty` | `품목번호`, `자재코드`, `소요량` |
| 단위 | kg | g |
| 숫자 형식 | `1500.5` | `1,500.5` |
| 시트·헤더 구조 | 단일 시트, 1행 헤더 | 복수 시트, 2행 병합 헤더 |
| 날짜 형식 | `2026-11-30` | `2026.11.30` |

(구체 값은 E01에서 정의)

### 2.3 단일 정답 원천 (Canonical Source)

- 모든 형식(CSV, XLSX, DOCX, PDF, HWP/HWPX)은 **하나의 정답 원천(canonical JSON)**에서 파생한다.
- 정답 원천은 파서 실험 시작 전에 동결(freeze)하고 SHA-256 해시와 버전을 기록한다. 이후 변경 시 정답셋 버전을 올리고 이전 결과는 `INVALID` 또는 재실행 대상으로 표시한다.
- 문서 생성 코드와 평가(채점) 코드는 분리하며, 정답 원천의 일부(최소 10%, 비율은 팀 합의 필요)는 사람이 원본 문서와 육안 대조한다.

### 2.4 오류 주입 목록

정상 데이터셋과 별도로, 아래 오류를 **의도적으로 주입한 데이터셋**을 만든다. 각 주입 오류는 고유 ID와 위치(파일/행/필드)를 정답 목록(`injected_errors`)에 기록한다.

| 코드 | 오류 유형 | 주입 예 | 주 평가 실험 |
|---|---|---|---|
| ERR-MISSING | 필수값 누락 | BOM 행의 `qty_per_unit` 비움 | E02, E05, E06, E07 |
| ERR-DUPID | 중복 ID | 서로 다른 자재에 동일 `material_id` | E02, E05, E06, E07 |
| ERR-BADREF | 잘못된 제품·자재 참조 | BOM의 `material_id`가 자재 마스터에 없음 | E05, E06, E07 |
| ERR-UNIT | 단위 불일치 | 동일 자재를 kg/g 혼용, 단위 누락 | E02, E05, E06 |
| ERR-NUMFMT | 숫자 형식 오류 | `1,5OO`(문자 O), `12kg`(값·단위 혼합), 음수 수량 | E02, E05, E06 |
| ERR-TABLE | 표 행·열 구조 손실 | 병합 셀, 줄바꿈 셀, 페이지에 걸친 표 | E03, E04 |
| ERR-IDVER | 제품 ID 또는 문서 버전 손실 | 머리말/표 제목에만 있는 제품 ID·버전 | E03, E04 |
| ERR-DATE | 잘못된 날짜 | 존재하지 않는 날짜, 납기 < 주문일, 유효 종료 < 시작 | E05, E06 |
| ERR-BOMCYCLE | BOM 순환 참조 | 반제품 A→B→A | E05, E06, E07 |
| ERR-BOMVER | BOM 버전 충돌 | 같은 제품의 활성 버전이 기간·수량·사이트 조건에서 동시에 겹쳐 선택 모호, 적용 버전 없음, 미승인 버전 활성 | E05, E06 |
| ERR-INVQTY | 재고 수량 오류 | 음수 재고, 할당 > 보유, EA 단위 소수 수량 | E05, E06 |
| ERR-RESREL | 제품–생산설비 관계 오류 | 존재하지 않는 자원 참조, 공정 없는 제품, 공정에 없는 자원으로 계획 | E05, E06, E07 |

- ERR-DATE 이하 5개 코드는 E01 명세에서 추가했다. 규칙별 탐지 방법은 [manufacturing_data_schema.md](manufacturing_data_schema.md) §5.
- ERR-TABLE, ERR-IDVER는 데이터 오류가 아니라 **파싱 과정의 손실 위험**을 보기 위한 문서 구조 케이스다.
- 주입 개수와 유형별 건수는 `팀 합의 필요`. 유형별 최소 1건 이상을 원칙으로 한다.
- 정상 데이터에 대한 오탐(False Positive)을 보기 위해, 주입하지 않은 정상 레코드도 동일하게 검증 대상에 포함한다.

## 3. 문서 파싱 평가 지표 (E02, E03, E04)

### 3.1 비교 전 정규화 규칙

비교는 정규화 후 수행하며, 정규화 규칙은 모든 파서에 동일하게 적용한다.

| 항목 | 규칙 |
|---|---|
| 공백 | 앞뒤 공백 제거, 연속 공백 1칸, 셀 내 줄바꿈 → 공백 |
| 유니코드 | NFC 정규화, 전각/반각 숫자 통일 |
| 숫자 | 천 단위 구분자 제거 후 Decimal 비교. 유효숫자·소수 자릿수는 정답 원천 기준 |
| 단위 | 표기 변형만 통일(`KG`→`kg`, `㎏`→`kg`). **단위 환산(g→kg)은 하지 않는다** (보존 여부를 보기 위함) |
| 날짜 | 정답 원천 형식(ISO 8601)으로 파싱 가능하면 일치로 본다 |

정규화로 일치하게 된 건수도 별도로 기록한다(원문 그대로 일치 / 정규화 후 일치 구분).

### 3.2 지표 정의

| 지표 | 정답 단위(분모 단위) | 계산식 | 분모 0 처리 | 비고 |
|---|---|---|---|---|
| 필수 필드 정확 일치율 | 문서별 정답 필수 필드 1개 | 정규화 후 정답과 일치한 필수 필드 수 / 정답 필수 필드 총수 | `N/A(분모 0)` | 필수 필드 목록은 E01에서 확정 |
| 필수 필드 누락률 | 동일 | 출력에서 찾을 수 없거나 빈 값인 필수 필드 수 / 정답 필수 필드 총수 | `N/A(분모 0)` | 일치율 + 누락률 + 오값률 = 1 (오값률 = 값은 있으나 틀림) |
| 표 셀 정확 일치율 | 정답 표의 셀 1개 | (행, 열) 위치가 같고 값이 일치한 셀 수 / 정답 셀 총수 | `N/A(분모 0)` — 표 없는 문서 | 표 대응은 정답 표 ID 기준으로 매칭(순서·제목). 매칭 실패 표의 셀은 모두 불일치 처리 |
| 표 셀 내용 일치율(보조) | 동일 | 위치와 무관하게 값 다중집합이 일치한 셀 수 / 정답 셀 총수 | 동일 | 구조는 깨졌지만 내용은 남은 경우를 구분 |
| 표 행·열 구조 보존 여부 | 정답 표 1개 | 표별 True/False (판정 조건은 §3.4). 보존율 = True 표 수 / 정답 표 수 | `N/A(분모 0)` | 병합 셀은 §3.4, 페이지를 넘어가는 표는 §3.5 규칙 적용 |
| 숫자·단위 보존율 | 정답의 (값, 단위) 쌍 1개 | 값과 단위가 같은 셀/필드 안에서 모두 정확히 보존된 쌍 수 / 정답 쌍 총수 | `N/A(분모 0)` | 값만 보존, 단위만 보존은 별도 건수로 기록 |
| 처리시간(초) | 파일 1개 × 1회 실행 | `time.perf_counter()` 기준 파서 호출 시작~결과 반환 경과시간. 반복 측정의 중앙값과 최소·최대 | 해당없음 | 반복 횟수는 기본 3회 제안(팀 합의 필요). 첫 실행(cold)과 이후(warm) 구분. API는 네트워크 포함 왕복시간 |
| CPU 최대 메모리 사용량 | 파일 1개 처리 | 파서 실행 프로세스의 피크 RSS(MB). 별도 자식 프로세스로 파서를 실행하고 관찰 | 해당없음 | §3.3 측정 범위 참고 |
| API 호출 수 | 파일 1개 | 클라이언트 로그에 기록된 요청 수(재시도 포함, 재시도 별도 열) | 해당없음(로컬 파서) | |
| 실제 청구 가능 비용 | 실행 1회 전체 | 공급사 콘솔·청구서에서 확인한 금액만 기록 | — | 확인 전 `미확인`. 단가×페이지 계산값은 "산출 비용(공식 단가 기준, 출처·확인일)" 별도 열로만 표기하고 실제 비용 칸에 넣지 않는다 |
| 실패율 | 파일 1개 | `run_ok = False` 또는 `output_generated = False` 파일 수 / 시도 파일 수 | `N/A(분모 0)` | 타임아웃 기준값은 팀 합의 필요 |
| 오류 복구 여부 | 실패 파일 1개 | 재시도·대체 경로(fallback)로 정상 출력을 얻었는지 Y/N 및 방법 | `N/A(실패 없음)` | 복구 후 정확도는 별도 계산 |

### 3.3 메모리 측정 가능 범위

| 방식 | 측정 대상 | 한계 |
|---|---|---|
| psutil로 자식 프로세스 RSS 주기 샘플링(예: 50ms) | 파서 프로세스 + 자식 프로세스 | psutil 미설치(2단계 설치 승인 필요). 샘플링 간격보다 짧은 피크는 놓칠 수 있음 |
| Windows `Get-Process` PeakWorkingSet64 | 단일 프로세스의 OS 기록 피크 | 자식 프로세스 미포함 |
| `tracemalloc` | Python 힙 할당 | C 확장(PyMuPDF 등)의 네이티브 메모리 미포함 → 피크 RSS 대체 불가 |
| 외부 API | 클라이언트 측만 측정 가능 | 서버 측 자원은 `측정불가(서버 측)` |
| Java 기반 도구(GraphDB) | JVM 프로세스 RSS | JVM 힙 설정(-Xmx)에 따라 달라짐. 설정값을 함께 기록 |

결과에는 사용한 측정 방식을 반드시 명시한다.

### 3.4 병합 셀과 표 구조 보존 판정 규칙

**정답 표현** — 정답 원천의 표는 논리 격자(행 수 × 열 수)와 병합 영역 목록(`top, left, rowspan, colspan`)으로 정의한다. 병합 영역의 값은 좌상단 셀(앵커)에만 둔다. 2행 이상 병합 헤더도 같은 방식으로 표현한다.

**병합 셀 값 판정**

| 셀 | 일치 조건 |
|---|---|
| 앵커 셀 | 정규화 후 값이 정답과 같음 |
| 병합 영역 안의 비앵커 셀 | 빈 값이거나 앵커 값과 같음 (파서마다 "좌상단만 값" 또는 "전체 칸 복제" 방식이 다르므로 둘 다 허용) |
| 병합 영역 밖 셀 | 정규화 후 값이 정답과 같음 |

- 표 셀 정확 일치율의 분모는 **정답에서 값이 있는 셀 수**이며, 병합 영역은 앵커 1개로 센다. 정답이 빈 셀에 값이 들어간 경우는 `삽입 셀 수`로 별도 기록한다.
- 병합 정보(span)를 출력하는 파서는 병합 영역 일치 수 / 정답 병합 영역 수를 별도 기록한다. 병합 정보를 출력하지 않는 파서는 `해당없음(병합 정보 미제공)`으로 적고 위 셀 규칙으로만 평가한다.

**표 구조 보존 True 조건** (모두 충족)

1. 정답 표와 출력 표의 매칭에 성공 (정답 표 ID 기준)
2. 논리 행 수와 열 수가 정답과 같음 (병합을 펼친 격자 기준)
3. 헤더 행의 수와 위치가 같음
4. 데이터 행의 순서가 같음

병합 처리 방식(빈칸/복제) 차이만으로는 구조 보존 실패로 보지 않는다. 행·열이 밀리거나 병합 셀 때문에 열이 추가·삭제되면 실패로 본다.

### 3.5 페이지를 넘어가는 표

- 정답 원천에서 여러 페이지에 걸친 표는 **하나의 논리 표 ID**로 정의하고, 페이지별 행 범위와 다음 페이지 반복 헤더 여부를 함께 기록한다.
- 평가 항목:

| 항목 | 기록 값 |
|---|---|
| 연결 여부 | `연결`(한 표로 출력) / `분리`(페이지별 별도 표) / `일부 누락`(어느 페이지 구간이 출력되지 않음) |
| 원출력 기준 점수 | 파서 출력을 그대로 채점. 분리된 경우 첫 조각만 정답 표와 매칭되고 나머지 행은 누락으로 처리 |
| 후처리 연결 기준 점수(보조) | 분리된 조각을 페이지 순서대로 이어붙여 채점. 파서 자체 성능과 구분해 "후처리 적용" 표시 |
| 반복 헤더 처리 | 이어붙일 때 반복 헤더가 데이터 행으로 들어가면 `삽입 행 수`로 기록 |
| 페이지 경계 행 손상 | 경계에서 한 행이 잘리거나 두 행으로 나뉜 건수 |

- 표 구조 보존 True는 **원출력 기준 `연결`인 경우에만** 줄 수 있다.

### 4.1 탐지 판정 및 집계 규칙

**식별 단위**

- 레코드: 원본 파일 + 기본키(기본키가 없거나 손상된 경우 원본 행 번호). 중복 ID 오류처럼 여러 레코드가 관련되면 정답에 관련 레코드 집합을 적고, 그중 하나 이상을 지목하면 레코드 일치로 본다.
- 필드: 공통 스키마 필드명(매핑 후). 레코드 전체에 해당하는 오류(중복 ID, 레코드 누락 등)는 필드를 `*`로 표기한다.
- 유형: §2.4 오류 코드(ERR-MISSING 등). 검증 도구의 메시지는 채점 전에 오류 코드로 분류하며, 분류표(도구 메시지 → 오류 코드)를 결과와 함께 저장한다.

**정확한 탐지** — 채점기는 검증 도구의 오류 보고를 (레코드, 필드, 유형)으로 주입 목록과 대조해 오류 ID를 부여한다. **오류 ID, 레코드, 필드, 유형 4가지가 모두 대응될 때만** 정확한 탐지로 판정한다.

| 판정 | 조건 | 집계 |
|---|---|---|
| 정확한 탐지 | 4요소 모두 일치 | 탐지율 분자 |
| 부분 탐지 | 레코드는 일치, 필드 또는 유형 불일치 | 별도 기록 (분자 제외, 오탐 아님) |
| 미탐지 | 해당 오류 ID에 대응하는 보고 없음 | 탐지율 분모에만 포함 |
| 오탐 | 주입 목록 어디에도 대응하지 않는 보고 | 필드 수준·레코드 수준 오탐으로 각각 집계 |

**중복 오류 메시지 집계**

- 같은 오류 ID에 대응하는 보고가 여러 건이면 탐지 1건으로 센다. 나머지는 `중복 보고 수`로 기록하며 오탐으로 세지 않는다.
- 하나의 주입 원인 때문에 다른 레코드·필드에 연쇄로 생기는 보고(예: 중복 ID 때문에 BOM 참조가 모호해짐)는, E01에서 주입 목록에 `derived_effects`(예상 파생 보고)를 미리 정의해 `파생 보고 수`로 분류한다. 이 보고는 탐지율과 오탐에 넣지 않는다.
- 미리 정의되지 않은 파생 보고는 사람이 검토해 파생/오탐으로 분류하고, 분류 근거를 `failures.md`에 남긴다.
- 같은 (레코드, 필드)에 대한 오탐 메시지가 여러 건이면 필드 수준 오탐 1건으로 센다.

**필드 수준과 레코드 수준 오탐 분리** — 필드 수준 오탐은 "어느 값이 잘못 의심되었는가", 레코드 수준 오탐은 "정상 레코드 중 몇 건이 사람 검토로 넘어가는가"를 본다. 두 값을 항상 함께 보고한다.

## 5. 온톨로지·저장 방식 비교 평가 (E05, E06, E07)

### 5.1 비교 대상

| 방식 | 구현 범위 |
|---|---|
| A | 공통 JSON + Pydantic 검증 + 관계형 SQL(SQLite 등, 확정은 E05) |
| B | RDFLib로 RDF 트리플 생성 + pySHACL 검증 + RDFLib 내 SPARQL |
| C | B와 동일한 RDF를 GraphDB에 적재 후 SPARQL 조회 |

- 세 방식 모두 **동일한 정답 사실과 동일한 주입 오류**를 입력한다.
- 온톨로지가 SQL보다 우수하다는 가정을 하지 않는다. A를 Baseline으로 둔다.
- OWL 추론(reasoner)은 SHACL/SQL로 해결되지 않는 요구가 확인되기 전까지 구현하지 않는다.

### 5.2 관계 조회 질의셋 (초안, E01에서 확정)

| ID | 질의 | 단계 |
|---|---|---|
| Q1 | 제품 P의 BOM 자재 목록과 소요량 | 1단계 |
| Q2 | 자재 M을 사용하는 모든 제품 | 1단계(역방향) |
| Q3 | 주문 O 충족에 필요한 자재별 총소요량(단위 통일) | 2단계 + 계산 |
| Q4 | 재고가 주문 소요량보다 부족한 자재와 부족량 | 3단계 + 계산 |
| Q5 | 리드타임이 기준일 이상인 자재를 포함하는 제품 | 2단계 |

- E01에서 Q1~Q5는 Competency Questions(CQ-01~CQ-20)로 확장·흡수했다. 대응표는 [ontology_competency_questions.md](ontology_competency_questions.md) §2.

## 7. 실험 상태 관리

| 상태 | 의미 | 전이 조건 |
|---|---|---|
| NOT_STARTED | 미실행 | 초기값 |
| RUNNING | 실행 중 | 실행 시작 기록 시 |
| COMPLETED | 실행 완료 및 결과 확보 | 결과 파일·메타데이터·로그가 모두 저장됨 |
| BLOCKED | 실행 장애 | 선행조건 미충족, 도구 설치 불가, 승인 대기 등. 사유 기록 |
| INVALID | 비교 조건 또는 측정 결과에 문제 발견 | 정답셋 변경, 입력 불일치, 측정 오류 발견 시. 사유와 재실행 계획 기록 |

`COMPLETED`는 기술 채택을 의미하지 않는다. 채택 판단은 `decisions.md`의 규칙을 따른다.

## 8. 결과 파일 공통 형식

- 결과 위치: `results/<실험ID>_<이름>/` (디렉터리는 2단계 이후 생성)
- 필수 파일:
  - `run_meta.json` — §1.3 메타데이터
  - `metrics.csv` — 행 = 파일×도구(또는 질의×방식), 열 = §3~§5 지표 + 분자/분모
  - `failures.md` — 실패·오추출 사례(원본 위치, 기대값, 실제값, 원인 추정은 "가설"로 표기)
  - `summary.md` — 결과 요약과 판단 근거 (결과 해석과 사실 기록 구분)
- 로그·원시 출력은 `raw/` 하위에 보관. 외부 API 응답은 합성 데이터에 한해 저장.

## 9. E00 재현성 평가 기준

E00은 정확도 지표(§3~§5)를 적용하지 않는다. 대신 **환경 안정 필드 비교**로 재현성을 판정한다.

| 항목 | 규칙 |
|---|---|
| 비교 방법 | `scripts/check_environment.py`를 같은 가상환경에서 별도 프로세스로 2회 실행해 `env_check_run1.json`, `env_check_run2.json` 생성 후 비교 |
| 비교 대상(안정 필드) | Python 실행 경로·버전·구현·비트, OS 이름·릴리스·버전·에디션·DisplayVersion·아키텍처, CPU 모델·물리/논리 코어 수, 전체 RAM, 가상환경 사용·프로젝트 가상환경 여부·전역 site-packages 포함 여부, pytest/psutil 버전, 설치된 전체 배포판 목록과 버전, Git 설치 여부·버전, 프로젝트 루트 경로·이름·Git 저장소 여부 (정확한 목록은 `check_environment.py`의 `STABLE_FIELDS`) |
| 제외(변동 필드) | 실행 시각, 실행 소요시간, 가용 RAM(바이트·비율), 수집 오류 목록 |
| 일치 판정 | 모든 안정 필드 값이 같아야 일치. **필드 누락 또는 `null`(미측정)은 양쪽이 같아도 불일치**로 본다 |
| 추가 확인 | pytest 전체 통과, `requirements.lock`과 설치 패키지 버전 일치, 출력 JSON에 사용자 홈 경로·사용자 이름 없음 |
| 상태 판정 | 점검 스크립트 또는 pytest 실행 불가 → `BLOCKED` / 테스트 실패·안정 필드 불일치·필수 필드 미측정 → `INVALID` / 그 외 → `COMPLETED` (`scripts/run_e00.py`가 자동 판정) |

가용 RAM은 비교하지 않지만 매 실행 값을 기록한다. 이후 성능 측정 실험(E02~E07)에서 측정 당시 가용 RAM을 함께 남기는 근거로 쓴다.

## 10. 문서 형식별 검증 항목과 지표 (E02~E04, 2026-10-20 추가)

전체 파싱 검증 범위는 **CSV, XLSX, DOCX, PDF, HWP, HWPX, PPTX** 7개 형식이다. 모든 파서 출력은 [intermediate_representation.md](intermediate_representation.md)의 중간 JSON으로 맞춘 뒤 같은 채점기로 평가한다. §1(기록 규칙), §3.2(공통 지표), §3.4(병합 셀), §3.5(페이지 넘김 표), §4.1(탐지 판정)은 모든 형식에 그대로 적용한다.

### 10.1 형식별 검증 항목

| 형식 | 실험 | 필수 검증 항목 | 형식 고유 위험 |
|---|---|---|---|
| CSV | E02 | 인코딩(UTF-8/UTF-8-BOM/CP949)·구분자 판별, 헤더, 숫자·날짜 서식, 선행 0 | 인코딩 오인, 쉼표 포함 값 |
| XLSX | E02 | 시트 선택, 병합 헤더 복원, 텍스트 셀 선행 0, 날짜 셀 | 병합 셀, 숨김 행, 표시 형식과 실제 값 차이 |
| DOCX | E03 | 문단 순서, 표 셀·병합, 머리말·꼬리말·각주의 제품 ID·문서 버전 | 중첩 표, 텍스트 상자 누락 |
| PDF (텍스트형) | E03, E04 | 페이지·좌표, 표 검출·셀 구조, 페이지 넘김 표, 머리말의 ID·버전 | 표가 줄 단위 텍스트로 풀림, 읽기 순서 뒤섞임 |
| PDF (스캔) | E04 | 텍스트 레이어 없음 판정, OCR/API 결과의 표·숫자·한글 | 빈 출력, 숫자·단위 오인식 |
| HWP | E03 | 열림 여부, 문단·표 추출, 표 병합, 문서 버전 | 배포용·암호 문서, 버전별 미지원 |
| HWPX | E03 | 섹션 XML 파싱, 표 구조, 문단 순서 | 패키지 구조 변형 |
| PPTX | E03 | 슬라이드·도형 순서, 표 도형 셀, 텍스트 상자, 그룹 도형, 발표자 노트 | 도형 배치 순서와 읽기 순서 불일치, 이미지 속 표 |

### 10.2 추가 지표 (문서 형식)

| 지표 | 정답 단위 | 계산식 | 분모 0 처리 |

### 10.3 원본 위치 보존 판정 (형식별)

| 형식 | 성공 조건 | 부분 성공 |
|---|---|---|
| CSV / XLSX | (시트,) 행·열이 정답과 같고 그 셀 원문이 출력 원문과 같음 (E02 방식) | 행은 맞고 열 정보 없음 |
| DOCX | 본문 요소 순번(또는 표 번호·행·열)과 part(본문/머리말/각주)가 정답과 같음 | 요소는 맞고 part 불일치 |
| PDF | 페이지가 같고 출력 bbox와 정답 bbox의 IoU ≥ 임계값 (**임계값 팀 합의 필요**), 좌표계(원점·단위)를 맞춘 뒤 비교 | 페이지만 일치 |
| HWP | 섹션·문단 번호(표는 컨트롤 순번·행·열)가 정답과 같음 — 도구별 번호 체계를 정답 작성 시 같은 도구 기준으로 기록 | 섹션만 일치 |
| HWPX | 섹션 파일과 문단 ID(또는 XPath), 표 번호·행·열이 같음 | 섹션 파일만 일치 |
| PPTX | 슬라이드 번호와 도형 ID(표는 행·열)가 같고 part(슬라이드/노트)가 같음 | 슬라이드만 일치 |

### 10.4 정답 확보 규칙

- 원본 파일이 아직 없는 형식(DOCX, PDF, HWP, HWPX, PPTX)은 **샘플 확보·생성 계획만** 세우고, 측정 전에는 모든 지표를 `미측정`으로 둔다. 계획은 [experiment_plan.md](experiment_plan.md) E03 "문서 샘플 확보 계획".
- 정답 위치(bbox·도형 ID 등)는 생성 도구가 아는 값(생성 시 기록) 또는 사람이 원본 뷰어에서 확인한 값으로 만들고, 평가 대상 파서의 출력으로 정답을 만들지 않는다.
- HWP는 [experiment_plan.md](experiment_plan.md) E01 "HWP 정답 원천 예외"의 독립 검수 규칙을 따른다.
