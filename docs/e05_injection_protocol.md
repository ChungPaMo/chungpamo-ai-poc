# E05 오류 주입 프로토콜 — 평가셋 v1

> 작성 2026-10-21. 생성기 `scripts/e05_build_eval_set.py`, 산출 `data/canonical/e05/`. 기준 데이터 `data/canonical/ground_truth_v2.json` (sha256 `262dbe75dbfaf8c0c32003144d62e0b2057c61187dce4b548a457cf8819fc48e`, 변경 없음).

## 1. 원칙

1. **정상과 오류 분리**: 정상 데이터는 E01 정답셋 v2 그대로(`clean`). 오류 데이터는 정상 데이터에 변경 연산을 적용해 매번 새로 만든다. 데이터셋 본문은 저장하지 않고 명세(연산)와 해시만 저장한다.
2. **정답은 검증기와 독립**: 기대 규칙·레코드·필드는 생성기 명세에서만 정한다. 검증기(`e05_validate_*.py`)는 평가셋 정답을 읽지 않으며(테스트로 확인), 채점기(`e05_score.py`)는 검증기를 import하지 않는다.
3. **주입 실재 확인은 다른 코드로**: ① 정상 데이터와의 상태 비교(diff) — 바뀌지 않은 연산(noop), 선언하지 않은 변경, 추가 레코드 불일치가 있으면 실패 ② 관계형 오류(순환·버전 겹침·BOM 선택·우선 공급사·배분 합·공정 없음)는 생성기 안의 별도 조건 함수로 오류 조건이 실제 성립하는지 확인. 결과 `verification_v1.json` (72/72 ok).
4. **재현성**: 난수를 쓰지 않는 결정적 연산. 새 레코드 record_uid = `rec_` + sha256("e05|데이터셋|연산 번호") 앞 16자리. `seed` 20261021과 작성일은 명세에 고정 기록(재생성 시 같은 해시 확인).
5. **규모**: E01 규모(353 레코드)를 그대로 쓰고 데이터셋당 1~10개 연산만 적용. 대량 데이터는 성능 측정용 복제(§6)에만 쓴다.
6. **새 사실 금지**: 오류 값은 기존 문서의 규칙을 위반하도록 만든 합성 값이다. 근거 없는 규칙(합성 가정)은 WARNING으로만 주입한다.

## 2. 기록 항목 (데이터셋별, `eval_set_v1.json`)

| 요구 항목 | 필드 |
|---|---|
| 원본 데이터 ID | `ops[].where` (업무 키), `injection_record[].record_uid` |
| 오류 주입 위치 | `injection_record[]` — 엔터티·record_uid·필드 |
| 오류 유형 | `error_code` (evaluation_protocol §2.4 + E05 추가 ERR-ENUM·ERR-IDFMT) |
| 원본 값 / 변경 값 | `injection_record[].old` / `.new` (추가·삭제는 kind로 구분) |
| 기대 검출 규칙 | `truth.expected[]` — (rule, record_uids, field) |
| 예상 심각도 | `severity` (ERROR / WARNING) |
| 연쇄 영향 | `truth.derived[]` (예: BOM 기간 변경 → 계획 라인 B06 선택 불가 11건), `truth.acceptable[]` (같은 원인으로 다른 규칙이 보고해도 오탐 아님) |
| 경계 조건 여부 | `boundary_case` |
| 상호작용 | `interaction_note` (복합 데이터셋) |

규모·해시: `manifest_v1.json` — eval_set sha256 `d666c1600267e8de59a73a865f749487f3438f809c62b210eb83a99411db28c7`, 데이터셋별 sha256(정렬된 압축 JSON), 레코드 수.

## 3. 구성 (72개, 기대 항목 80개)

| 종류 | 수 | 내용 |
|---|---|---|
| clean | 1 | 정답셋 v2 그대로. 모든 방식에서 ERROR·WARNING 0이어야 함 (V13 생산능력 초과 6건은 의도된 계산 결과 → INFO) |
| single | 59 | 채점 대상 규칙 41개 전부를 1회 이상 단독 주입 (ERROR 54, WARNING 5) |
| pass | 9 | 경계 통과 — 규칙 경계에 걸치지만 정상이어야 하는 값 (ERROR가 나오면 오탐) |
| compound | 3 | 독립 오류 5개(C-1), 상호작용(C-2), 같은 레코드 다중 오류(C-3) |

오류 코드별 단일 주입 수(WARNING 포함, 합 59): ERR-BADREF 8, ERR-BOMCYCLE 2, ERR-BOMVER 9(그중 WARNING 1: I-B09), ERR-DATE 6(WARNING 1: I-V12), ERR-DUPID 6(WARNING 1: I-B10), ERR-ENUM 2, ERR-IDFMT 1, ERR-INVQTY 4, ERR-MISSING 5(WARNING 1: I-S07), ERR-NUMFMT 7, ERR-RESREL 6(WARNING 1: I-V11), ERR-UNIT 3.

### 3.3 복합 데이터셋의 상호작용

- **C-1**: 서로 다른 엔터티의 독립 오류 5개(I-S01a, I-R02a, I-V02, I-B02c, I-S04a 연산 결합). 사건 5개.
- **C-2**: 자재 삭제(고아 참조 3건) + 자재 ID 중복 + BOM 라인 전부 삭제 뒤 순환 라인 추가. 라인 삭제(I-B09) 뒤 순환 라인이 추가되어 SF002 BOM 라인이 1개가 되므로 **B09(라인 없음)는 성립하지 않아 정답에서 뺐다** — 연산 순서가 정답을 바꾸는 사례.
- **C-3**: 같은 레코드에 여러 오류 — 주문 O015(날짜·상태·제품), 재고 M009(음수·단위·기준일), BOM FG002-V1(상태 소문자 + 종료일 < 시작일). Pydantic은 필드 오류가 있으면 model_validator를 실행하지 않으므로 B05가 가려질 수 있다 — **정답에는 포함**(가려지는 것 자체를 측정).

## 4. 정답 판정 단위

- 기대 항목 = (규칙, record_uid, 필드). 필드 `*`는 레코드 단위 규칙(중복·순환 등).
- 사건 = 주입 1건(복합 데이터셋은 구성 단일 주입별, C-3은 1건). 사건 검출 = 그 사건의 기대 항목 중 1개 이상 검출.
- 판정 분류와 TN 근사는 [e05_score.py](../scripts/e05_score.py) 머리말과 [e05_validation_scope.md](e05_validation_scope.md) §6.

## 5. 알려진 정답 정의 한계

- `acceptable`의 `record_uids: null`은 "주입 대상 레코드"만 뜻한다. I-S08c(복합 키 중복)에서 **원래 레코드** 쪽 B10(같은 구성품 중복, 합성 가정 WARNING) 보고는 정답 정의상 오탐 1건으로 집계된다. 결과를 본 뒤 정답을 고치지 않고 그대로 보고한다 (평가셋 v2에서 수정 후보).
- 정답·검증기가 같은 규칙 카탈로그에서 나왔으므로, 카탈로그에 없는 오류 유형은 이 평가셋으로 측정되지 않는다.

## 6. 성능 측정용 확장 (정답 채점 대상 아님)

- S = ×1(353), M = ×10(3,494), L = ×50(17,454) 레코드. 업무 ID·참조 열에 `_i` 접미사, record_uid는 (배율, 복제 번호, 원래 uid) 해시로 재생성, Unit은 공유.
- 각 배율 데이터의 0번 복제본에 C-1 연산을 같은 방식으로 적용(오류 섞인 데이터). ×50 정상 데이터에서 ERROR·WARNING 0건(V13 INFO 300 = 6×50)을 확인했다.
