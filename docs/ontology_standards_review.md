## 2. 기술별 검토

### 2.1 RDF / RDFS
1. **해결하는 문제**: 서로 다른 출처의 데이터를 IRI로 식별되는 트리플(주어–술어–목적어)로 표현해 통합한다. RDFS는 클래스·속성·상하위 관계를 선언한다.
2. **과제 7 관련성**: 다른 업체(Vendor A/B)의 컬럼·ID를 같은 개념으로 매핑하는 문제(CQ-20), 관계 탐색(CQ-03, 05, 10).
3. **적용 필요**: 비교 대상 B·C의 전제이므로 E06에서 적용. MVP 채택 여부는 E06·E07 결과로 판단(1단계 원칙: 온톨로지 우수성 가정 없음).
4. **JSON/SQL 대체**: 대부분 가능. 매핑 테이블 + FK + 재귀 CTE로 같은 CQ에 답할 수 있다(설계상 예상, E05에서 확인).
5. **부담**: IRI·네임스페이스 정책 설계, 변환 스크립트, 레코드 노드 계층으로 인한 트리플 증가([provenance 설계 §6](data_provenance_design.md)).
6. **URL**: https://www.w3.org/TR/rdf11-concepts/ , https://www.w3.org/TR/rdf11-schema/

### 2.2 OWL 2
1. **해결하는 문제**: 클래스 동치·서로소·카디널리티 등 논리 공리와 추론(reasoner로 암묵 사실 도출, 일관성 검사).
2. **관련성**: 낮음. CQ는 사실 조회·계산·검증이며 추론이 필요한 질문이 없다. OWL은 열린 세계 가정이라 "필수값 누락" 같은 폐쇄형 검증에 맞지 않는다(검증은 SHACL 담당).
3. **적용 필요**: 1단계 결정대로 **추론 미적용**. `owl:Class`, `owl:ObjectProperty` 같은 선언 어휘만 사용할 수 있다.
4. **JSON/SQL 대체**: 해당 기능(선언) 수준에서는 스키마 정의로 대체 가능.
5. **부담**: 추론 적용 시 reasoner 선택·성능·결과 검증 부담이 큼. Protégé 사용 시 설치 필요(업무분장 기재).
6. **URL**: https://www.w3.org/TR/owl2-overview/

### 2.3 SHACL
1. **해결하는 문제**: RDF 그래프가 형태(shape) 조건을 만족하는지 검증하고 위반 보고서를 RDF로 출력한다. SHACL Core(카디널리티, 자료형, 값 범위, 속성 쌍 비교 등)와 SHACL-SPARQL(SPARQL 질의 기반 제약)으로 나뉜다.
2. **관련성**: 높음. [schema §5](manufacturing_data_schema.md)의 QR-01~08 검증을 RDF 방식으로 수행하는 수단.
3. **적용 필요**: E06 적용. 중복 ID·순환·기간 겹침 등은 SHACL-SPARQL이 필요할 것으로 예상(schema §5 표).
4. **JSON/SQL 대체**: 가능 — Pydantic 검증 + SQL 제약·질의(비교 대상 A).
5. **부담**: shape 작성, 위반 보고서를 원본 위치로 되돌리는 처리, pySHACL의 SHACL-SPARQL 지원 범위 확인(패키지 문서 [미조회]).
6. **URL**: https://www.w3.org/TR/shacl/

### 2.4 PROV-O
1. **해결하는 문제**: 개체(Entity)·활동(Activity)·행위자(Agent)와 생성·사용·파생 관계로 데이터 계보를 표현.
2. **관련성**: 높음. 원본 위치 역추적(CQ-19), 실제/합성 구분, 변환 이력.
3. **적용 필요**: E06에서 Starting Point 용어 중심으로 적용. 설계는 [data_provenance_design.md](data_provenance_design.md).
4. **JSON/SQL 대체**: 가능 — 추적 열(`record_uid`, `source_ref`, `transform_run_id`)과 실행 기록 표. RDF 방식에서는 PROV-O 어휘로 같은 정보를 표현해 공정하게 비교한다.
5. **부담**: 낮음~중간. 필수 속성이 정의되어 있지 않아 [확인] 최소 부분만 쓸 수 있다. 한정(qualified) 패턴은 필요 시에만.
6. **URL**: https://www.w3.org/TR/prov-o/

### 2.5 SOSA/SSN
1. **해결하는 문제**: 센서·관측·실행기(actuator)·샘플링과 관측 결과 표현.
2. **관련성**: 현재 없음. 설비 가동 데이터·센서 관측 CQ가 없고, 자원 능력은 계획값(시간)으로만 다룬다.
3. **적용 필요**: **미적용**. 수요기업이 설비 가동·센서 데이터를 제공하고 관련 의사결정 질문이 추가될 때 재검토.
4. **JSON/SQL 대체**: 해당없음(현재 불필요).
5. **부담**: 적용 시 관측 모델링 학습 부담.
6. **URL**: https://www.w3.org/TR/vocab-ssn/

### 2.6 QUDT
1. **해결하는 문제**: 단위·양의 종류·차원·환산 계수를 표준화된 IRI로 제공.
2. **관련성**: 중간. 단위 불일치(QR-03)와 환산이 필요하지만, PoC 단위는 kg·g·EA·h·day 수준이다.
3. **적용 필요**: **선택 적용**. 프로젝트 `Unit` 표를 기본으로 하고, 단위 IRI 상호운용이 필요하면 QUDT 단위 IRI를 대응 속성으로만 붙인다. QUDT 어휘 전체를 적재하지 않는다.
4. **JSON/SQL 대체**: 가능 — `Unit` 표(코드, 차원, 기준 단위, 환산 계수).
5. **부담**: QUDT 전체 적재 시 트리플 수 증가, 클래스 구조 학습. 단위 IRI만 참조하면 낮음. 라이선스 CC BY 4.0 → 출처 표기 필요 [확인].
6. **URL**: https://www.qudt.org/ (단위 어휘 기본 IRI http://qudt.org/vocab/unit [확인])

### 2.7 R2RML
1. **해결하는 문제**: 관계형 DB 테이블을 RDF로 바꾸는 매핑을 선언적으로 기술.
2. **관련성**: 낮음. PoC 원본은 CSV/Excel이고 SQL은 비교 대상 A일 뿐 RDF의 원천이 아니다.
3. **적용 필요**: **미적용**. 변환은 Python(RDFLib) 스크립트로 수행하고 변환 Activity를 PROV로 기록한다. 기업 ERP DB를 직접 RDF로 노출해야 하는 요구가 생기면 재검토.
4. **JSON/SQL 대체**: 해당없음(변환 스크립트로 대체).
5. **부담**: 매핑 엔진 선택·설치, Windows 실행 환경 확인 필요. CSV·JSON까지 다루는 RML은 W3C 표준이 아닌 커뮤니티 명세로 알려져 있음 [미조회].
6. **URL**: https://www.w3.org/TR/r2rml/

## 3. 온톨로지 구축 방법 비교 (A/B/C) — 조사만, 구현·API 호출 없음

### 3.1 비교 대상 정의

| 방식 | 정의 | 입력 | 산출 |
|---|---|---|---|
| A. 사람 직접 설계 | CQ와 도메인 지식으로 사람이 개념·관계를 정의 | CQ, 업무분장, ERP 문서(S1~S3) | 온톨로지 초안 |
| B. ERP 스키마·규칙 기반 생성 | 공통 데이터 스키마(이 문서의 schema)와 변환 규칙(테이블→클래스, FK→객체 속성, 연결 테이블→관계 클래스)으로 기계적 생성 | [manufacturing_data_schema.md](manufacturing_data_schema.md) | 스키마와 1:1 대응하는 온톨로지 |
| C. LLM 후보 추출 + 사람 검토 | LLM이 문서·컬럼명·샘플에서 개념·관계 후보를 제안하고 사람이 채택/수정/기각 | ERP 문서, 업체별 컬럼명, CQ | 후보 목록 + 검토 기록 + 온톨로지 |

### 3.2 조사된 LLM 기반 방법

| 방법 | 내용 | 출처 (조회 수준) |
|---|---|---|
| LLMs4OL (2023) | 온톨로지 학습을 용어 유형 분류(term typing), 분류 체계 발견(taxonomy discovery), 비분류 관계 추출 3개 과제로 나누고 9개 LLM 계열을 제로샷 프롬프트로 평가 | https://arxiv.org/abs/2307.16648 (검색 결과 요약으로만 확인, 원문 미조회) |

### 3.3 장단점 (과제 7 관점)

| 관점 | A. 사람 설계 | B. 스키마·규칙 생성 | C. LLM 후보 + 사람 검토 |
|---|---|---|---|
| CQ 적합성 | 높음 (CQ에서 출발) | 스키마가 CQ 기반이면 높음 | 후보가 CQ와 무관한 개념을 많이 포함할 수 있음 → 걸러내는 검토 필요 |
| 재현성 | 사람에 따라 달라짐 | 높음 (같은 입력 → 같은 출력) | 낮음 (모델·프롬프트·버전에 따라 달라짐. 실행 기록 보존 필요) |
| 새 기업 컬럼 대응 | 사람이 매번 매핑 | 규칙 추가 필요 | 낯선 컬럼명 후보 제안에 강점 가능성 (매핑·에이전트·보안 담당의 Tri-CHEF 매핑 실험과 겹침) |
| 비용·보안 | 사람 시간 | 낮음 | API 비용, 외부 전송 데이터 범위 관리 필요 (합성·공개 데이터만, 승인 후) |
| 검증 부담 | 리뷰 | 규칙 검토 | 후보 전수 검토 + 기각 사유 기록 필요 |
| 이번 PoC 규모(개념 10여 개) 적합성 | 충분 | 충분 (schema와 1:1이므로 사실상 A와 같은 결과) | 규모가 작아 이득이 드러나기 어려움 |

### 3.4 제안

- E06의 기본 온톨로지는 **B(스키마 기반 규칙 생성)**로 만들고 사람이 검토한다(A의 판단을 schema에 이미 반영했으므로 A와 B를 따로 구축할 실익은 작음).
- C는 **"새 업체의 컬럼명·용어를 기존 개념에 매핑하는 후보 제안"** 범위로 좁혀 평가하는 것이 과제 7 위험(다양한 기업 서식)과 맞다. 이는 매핑·에이전트·보안 담당의 Tri-CHEF·LLM 재판정 실험과 범위가 겹치므로, 중복 실험을 피하려면 **담당 조정이 필요**하다.
- C를 평가한다면 지표 후보: 후보 중 CQ에 필요한 개념 비율, 사람이 기각한 후보 비율과 사유, 누락된 필수 개념 수, 실행 간 결과 차이, API 호출 수·비용. 목표값은 팀 합의 필요.
- 이번 단계에서는 LLM API 호출·자동 생성기 구현을 하지 않았다.
