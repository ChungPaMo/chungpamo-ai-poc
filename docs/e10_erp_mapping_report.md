## 1. 모의 ERP 스키마와 E01 대응

- DDL `schemas/e10_mock_erp.sql` **v0.2** (SQLite STRICT, 18 테이블, 트리거 36개 = 본 테이블 11개 × INSERT·UPDATE·DELETE 3개 + 승인 기록 3개, §10 D-2 수정 반영). 본 테이블 11개 = E01 엔터티 11개(Product·Material·Supplier·SupplierMaterial·Unit·BOM·BOMLine·Order·Inventory·Resource·Operation), 필드명·타입·키는 E01 그대로. 주문 테이블 이름만 `SalesOrder`(SQL 예약어 회피).
- 생산능력은 E01대로 **시간 단위**(regular_hours_per_day 등). 제품 수량 기준 능력은 E01에 없으므로 만들지 않았다.
- 초기 적재: E01 v2의 ERP 엔터티 111건을 승인 기록(승인자 `SYSTEM_BOOTSTRAP`)과 함께 트리거를 거쳐 적재. 모의 ERP에서 되읽은 상태 = E01 정답셋 (데이터셋 해시 일치, E05 검증 오류 0).
- `PRAGMA foreign_keys = ON`을 연결마다 켜고 값 1을 확인.

## 2. 매핑 후보 구조

- 입력: 업체 A 형식(E02 설정 `configs/e02_vendor_mapping.json`의 헤더·코드표·날짜·숫자 형식) 행. 후보 = (테이블, 필드, 값, 방식, 검토 필요 여부), 원본 위치(file, sha256, row) 포함 → `MappingCandidate`.
- 구현한 비교군: 명시적 규칙(헤더 대응·코드표·사내 코드 정확 일치·품명 정확 일치), 마스터 기반 코드 검증, **E05 Python 검증기 그대로 재사용**(제안 레코드를 현재 모의 ERP 상태에 합쳐 검사).
- 미구현: BM25·임베딩·Tri-CHEF·LLM — 같은 평가셋으로 비교할 계약만 작성 (`schemas/e10_candidate_provider_contract.json`, §12).
- 흐름: 후보 → 값 검증(ValidationIssue, E05 규칙 ID) → StagingRecord(변경 전·후) → ApprovalLog(PENDING) → 승인·반려·보류 → 한 트랜잭션으로 본 테이블 + ChangeHistory.

## 12. Tri-CHEF 등 후보 제공자와 결합할 계약

`schemas/e10_candidate_provider_contract.json`: 요청(입력 행·원본 위치·`row_context`) → 응답(후보·순위·실제 점수·근거·`conflicts_with`). 제공자는 후보만 내고, 검증·staging·승인은 공통 단계가 한다. M13 결함 대응으로 `row_context`·`conflicts_with`를 계약에 넣었다. 공통 단계 진입점(`stage_candidates`)은 미구현 — 검색·에이전트 담당 결과 연결 시 구현 필요.
